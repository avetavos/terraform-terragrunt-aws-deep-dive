## ไอเดียในหนึ่งประโยค

Infrastructure as Code คือการอธิบาย cloud resource เป็นไฟล์ text แล้วเก็บไว้ใน version control แทนการคลิกผ่าน console ไฟล์นั้นคือ source of truth และมีเครื่องมือคอยทำให้ของจริงตรงกับไฟล์นั้น

## ปัญหาของ ClickOps

ลองนึกภาพ engineer คนหนึ่งเปิด AWS console แล้วสร้าง VPC, subnet สองสามอัน, EC2 instance และ security group ด้วยมือ มันก็ใช้งานได้ ผ่านไปสามอาทิตย์ อีกคนเปิด console แล้วแก้ rule ของ security group เพื่อปลด block การ deploy โดยไม่บอกใคร อีกเดือนถัดมามีคนลบ S3 bucket ที่ดูเหมือนถูกทิ้งไว้เฉย ๆ — แต่จริง ๆ มันไม่ได้ถูกทิ้งไว้เฉย ๆ

รูปแบบนี้มีชื่อเรียก มักพูดพร้อมสีหน้าเบ้ ๆ ว่า **ClickOps** จุดพังไม่ได้อยู่ที่คลิกไหนคลิกหนึ่งผิด แต่อยู่ที่ลำดับการคลิกทั้งหมดมันเป็นแบบนี้

- **Unrepeatable** ไม่มีใคร spin environment เดียวกันขึ้นมาใหม่จากศูนย์ได้ เพราะ "คำสั่ง" คือ muscle memory ของคนคนหนึ่ง
- **Undocumented** console แสดง state ปัจจุบัน แต่ไม่บอกว่า *ทำไม* มันถึงเป็นแบบนี้ หรือใครเป็นคนเปลี่ยน
- **Drift-prone** ทันทีที่มีสองคนเปลี่ยน account เดียวกันได้อย่างอิสระ state จริงกับภาพในหัวของแต่ละคนก็เริ่มเพี้ยนออกจากกันไปเรื่อย ๆ โดยไม่มีใครรู้ตัว

ไม่มีใครตอบได้ว่า "ตอนนี้ deploy อะไรอยู่จริง ๆ และทำไมถึงเป็นแบบนั้น" แค่อ่านอะไรสักอย่าง เพราะ console เองคือ source of truth เดียว และมันไม่มีความจำ ไม่มี review process ไม่มี diff ให้ดู

## Declarative เทียบกับ imperative

Infrastructure as Code (IaC) แก้ปัญหานี้ด้วยการทำให้ infrastructure ที่ต้องการเป็นไฟล์ commit เข้า git, review ผ่าน pull request เหมือนโค้ดทั่วไป และมีประวัติให้ `git blame` ย้อนดูได้ แต่เครื่องมือ IaC ไม่ได้ทำงานแบบเดียวกันหมด ความต่างตรงนี้สำคัญ

- **Declarative** IaC คุณอธิบาย end state ที่ต้องการ แล้วปล่อยให้เครื่องมือคิดเองว่าจะไปถึงยังไง Terraform เป็นแบบ declarative `resource` block บอกว่า "ควรมี S3 bucket ชื่อนี้ property แบบนี้" แล้ว Terraform คิดเองว่านั่นแปลว่าต้องสร้างใหม่ อัปเดต หรือปล่อยไว้เฉย ๆ
- **Imperative** IaC คุณเขียน script ของขั้นตอนตามลำดับ "สร้าง VPC ก่อน แล้วสร้าง subnet ข้างใน แล้ว launch instance ใน subnet นั้น" script อธิบาย *วิธีทำ* และเป็นหน้าที่คุณเองที่ต้องคอยดูให้มันถูกต้องตลอดเวลาที่อะไร ๆ เปลี่ยนไป รันซ้ำสองรอบอาจพังได้ถ้าแต่ละขั้นตอนไม่ได้ถูกเขียนให้รันซ้ำได้อย่างปลอดภัย

```hcl
# Declarative: describe the desired end state.
# Terraform decides what needs to change to get there.
resource "aws_s3_bucket" "reports" {
  bucket = "acme-monthly-reports"
}
```

```bash
# Imperative equivalent: an explicit, ordered command.
# Running this twice creates two buckets (if the name were unique)
# or errors out — the script itself has no idea what already exists.
aws s3api create-bucket --bucket acme-monthly-reports --region us-east-1
```

สังเกตว่าฝั่ง declarative ไม่มีคำว่า *create* เลยสักคำ กริยานั้นถูกตัดสินใจโดย Terraform ตอน plan จากสิ่งที่มันเจอจริง ๆ

## Terraform reconcile state ยังไง

loop หลักของ Terraform เป็นการเทียบสามทางแบบนี้เสมอ

1. อ่าน **real-world state ปัจจุบัน** ของ resource ที่มันจัดการอยู่ (มันเก็บ record ตรงนี้ไว้ใน state file)
2. อ่าน **configuration ที่ประกาศไว้** คือ HCL ที่อธิบายสิ่งที่คุณต้องการ
3. คำนวณ **plan** คือชุดของ create, update, destroy ที่น้อยที่สุดที่จำเป็น เพื่อทำให้ของจริงตรงกับ configuration

ไม่มีอะไรถูกทุบทิ้งแล้วสร้างใหม่ทั้งหมดแค่เพราะคุณเปลี่ยน argument เดียว ถ้าคุณแค่เปลี่ยน tag ของ instance plan ก็จะเป็นแค่ update in-place ที่ attribute เดียวนั้น ส่วนที่เหลือที่ Terraform จัดการอยู่จะไม่ถูกแตะต้อง

## ตำแหน่งของ Terraform

Terraform ไม่ใช่เครื่องมือ IaC ตัวเดียวในตลาด และควรรู้ไว้ว่ามันไม่ใช่อะไร

- **AWS CloudFormation** declarative เหมือน Terraform แต่ใช้ได้แค่กับ AWS ไม่มีทางเทียบเท่าที่จะจัดการ GCP project หรือ Datadog monitor ด้วย template เดียวกัน
- **Pulumi** เป็น provider-based และ state-tracked เหมือนกัน แต่คุณเขียนภาษาโปรแกรมมิ่งจริง ๆ (TypeScript, Python, Go) แทน HCL syntax แบบ declarative แลก learning curve ที่เล็กกว่ากับความยืดหยุ่นเต็มรูปแบบ (พร้อมความซับซ้อนเต็มรูปแบบ) ของภาษา general-purpose
- **Ansible** เป็นเครื่องมือ **configuration management** เป็นหลัก มัน login เข้าเครื่องที่มีอยู่แล้วรัน task ใส่มัน (ติดตั้ง package, แก้ config file, restart service) playbook ของมันในทางปฏิบัติค่อนไปทาง imperative มากกว่า คือ task เรียงลำดับรันจากบนลงล่าง และไม่มี state file ในตัวคอยบันทึกว่ามันสร้างอะไรไว้บ้าง

Terraform เจาะกลุ่ม **declarative, provider-based, state-tracked infrastructure provisioning** ด้วย plugin model (**provider**) ที่ทำให้ workflow และ HCL syntax เดียวกันไปจัดการ AWS, GCP, Azure, Kubernetes, Datadog และระบบอื่นอีกหลายร้อยตัวได้ พร้อม state file ที่บันทึกไว้ชัดเจนว่า Terraform รับผิดชอบอะไรบ้าง

อีกชื่อหนึ่งที่ควรรู้จักคือ **OpenTofu** หลังจาก Terraform เปลี่ยน license ในปี 2023 กลุ่ม contributor และบริษัทต่าง ๆ ได้ fork release เวอร์ชันโอเพนซอร์สล่าสุดออกมาเป็น OpenTofu ซึ่งตอนนี้ดูแลโดย Linux Foundation มันเป็น alternative แบบโอเพนซอร์สที่ compatible กัน — HCL syntax, provider และ workflow ที่เรียนในคอร์สนี้ใช้กับมันได้ตรง ๆ

<Callout title="สรุปหนึ่งบรรทัด">
Infrastructure as Code แทนที่การคลิกผ่าน console แบบทำซ้ำไม่ได้และไม่มีเอกสารด้วยไฟล์ text แบบ **declarative** ใน version control คุณอธิบาย *สิ่งที่ต้องการ* Terraform อ่าน real AWS state, diff กับ configuration ของคุณ แล้วคำนวณ **plan ที่น้อยที่สุด** ของ create, update, destroy — ต่างจากเครื่องมือแบบ imperative (script ของขั้นตอนเรียงลำดับ) หรือเครื่องมือ configuration-management อย่าง Ansible; **OpenTofu** คือ fork โอเพนซอร์สที่ compatible กันซึ่งควรรู้จักไว้
</Callout>
